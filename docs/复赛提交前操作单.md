# ListingReady 复赛提交前操作单

截至 2026-09-14，文本主流程已可演示；本文件用于完成参赛交付，不是已提交凭证。

## 一 先确认四项信息

1. 向组委会确认最终截止时间。用户提供的复赛模板写 9 月 15 日，初始公告写 9 月 13 日；不能自行解释为延期。
2. 确认团队名称“小宋1021队”、队长“宋翔宇”，补齐电话、邮箱、成员与角色。不要把密钥或私人邮件截图放进作品。
3. 决定评委体验方式。现有 Demo 只允许本人访问，直接粘贴私有链接不能证明评委可用。可按主办方要求另行授权指定评委，或采用允许的本地包与视频；任何开放权限都需明确确认。
4. 决定图片演示范围。现有 AI 重绘仍有细节偏差；可以如实展示实验和失败边界，不能把失败图包装成商品保真成功。

## 二 完成主流程复核

载入“厨房毛巾 · 官网资料” → 核对事实来源 → 生成 → 逐段核对文案与引用 → 删除没有证据的效果或款式承诺 → 重新检查。

当前公开资料案例只用于演示，并不代表团队拥有 IKEA 货品、品牌经销权或真实客户。

规则为零风险后仍需人工审核。队长确认内容后，亲自勾选“我已对照原始商品资料，人工检查全部文案与引用”，准备复核包。随后点击“保存 JSON 文件”，在下载目录打开文件，核对 `mode`、`humanReviewed`、文案、事实来源和风险报告。若未下载，可在完整预览中全选复制，使用 UTF-8 文本编辑器保存 `.json`，再检查文件能正常打开。

Markdown 审阅报告用于人阅读；JSON 是保留生成记录和结构化数据的完整版本。不得用修改 JSON 中的复核标记代替实际审核。

## 三 填写官方模板

原模板：`hackathon-复赛作品提交模板(2).docx`。正文使用 `复赛提交内容草稿.md`，不要直接提交操作日志。

按模板保留团队信息、业务价值、产品功能、技术架构、开发成果和提交链接等栏目。填写真实能力：多品类事实档案、比赛模型生成、独立风险检查、人工改稿、新旧对照、JSON 与 Markdown 导出。图片标为实验功能。不要声称已有客户、节约百分比、100% 准确率或自动上架。

最终 PDF 文件名：`小宋1021队_ListingReady_复赛作品.pdf`。逐页打开检查中文、表格、链接和分页；删除所有待填占位。当前仓库只有正文草稿，没有通过排版验收的正式 PDF。

## 四 录制 3 至 5 分钟视频

使用 `复赛演示脚本与验收清单.md` 的约 4 分钟流程。主线：事实 → 生成 → 查看引用 → 手动插入 waterproof 演示风险 → 删除错误并重检 → 保存文件。

手工插入的错误必须标为演示注入，不说成模型生成。剪掉等待时加“等待已缩短”说明。预录回放需说明，不伪装实时。不要录入密钥、邮件、私人文件路径或访问凭证。最终从头播放检查声音、清晰度、网址和下载文件。

## 五 备份与提交

代码配置见 README 和 `.env.example`。真实 Key 只在本地 `.env.local` 或托管 Secret，不随源码包、PDF、视频发送。接手者填写自己的授权密钥后运行 `npm install`、`npm run dev`；Node 推荐 24。

原 GitHub 推送目前需恢复凭据。源码已有私有 Sites 备份，具体版本见收尾日志末尾。若使用 GitCode，按官方模板决定是否授权指定评审账号；本项目不会自动创建仓库或授权。

提交前再次检查：PDF 可读、视频可播放、Demo 用非所有者账号可访问或本地材料满足要求、联系人完整、文件名正确、模型与局限说明真实、无密钥。提交后保存组委会回执。没有回执不标记“提交成功”。
